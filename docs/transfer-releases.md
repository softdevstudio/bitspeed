# Transfer release coverage

Transfer uses its own transfer/version.go, transfer/vX.Y.Z tags and bitspeed-transfer archive names. Inspect keeps its existing independent version and release. Version 0.1.0 was selected after independent review, exact-source candidate CI 39391488194 and five clean packaging/three native gates in Release Transfer 39391730821 passed. That 0.0.0-dev run skipped publication. Stable publication must repeat all exact-source gates; a development version cannot publish.

## Platform scope

Linux amd64 and macOS arm64 have native delivery checks on CI local filesystems: preparation, upload, complete digest/publication, receipt caching, process restart and same-ID retry. Separate executable tests kill sender and receiver during a partial chunk, after accepted chunk publication before response delivery and after final publication before its response. Each resumes from the same immutable snapshot with the original source removed, verifies one complete output and a stable receipt, and confirms verified chunk identity was retained. A packaged TLS listener test uses a locally trusted certificate; the Go client test exercises certificate-verified HTTPS delivery and rejection of an unrelated certificate. No insecure mode exists.

Linux arm64 and macOS amd64 are cross-built only; there is no native runtime or filesystem crash coverage for those variants. Up to 0.3.0, Windows amd64 was a compatibility archive for version/help and explicit unsupported-operation behavior only. From 0.4.0 Windows amd64 has native delivery coverage on the runner's local NTFS volume: the whole Go test suite including process-kill recovery tests, race-enabled tests, and the executable delivery, interruption and TLS checks run on windows-latest in CI and again on the packaged archive before publication. docs/windows-persistence.md describes the Windows persistence calls and their limits. BUILD_INFO.json and release verification metadata distinguish these limits.

The supported filesystem families and root trust requirements are in receiver-staging.md. Native runner tests do not establish every filesystem/mount/hardware power-loss guarantee. The implementation relies on checked file and directory synchronization and no-replace hard links. Fixed five-minute operation/startup bounds can fail safely on large/slow storage. The 64 GiB manifest bound is a protocol maximum, not a tested throughput or completion-time promise.

## Automated release gate

Release Transfer is triggered only by successful exact-commit main CI. It shares the bitspeed-release concurrency group with Release Inspect. The shared builder in scripts/release_inspect.py selects the product explicitly with --product transfer; the default remains inspect. Five clean CGO-disabled archives are built with the exact go.mod toolchain. All five provenance/package jobs and three native smoke jobs must succeed before the publisher can create or resume a draft. All three native gates run the executable delivery, interruption and TLS smoke checks; up to 0.3.0 the Windows gate ran version/help and unsupported-operation checks only.

The publisher rechecks exact-source main CI and current HEAD, verifies clean archive provenance, records operational/native/cross-build limits, creates a source-bound immutable product tag and uploads a draft. It downloads every uploaded asset and compares checksums before publishing. A published version is immutable and skipped on later pushes. A failed unpublished tag cannot move to another source; use a fresh version after fixing source. No manual publication is part of the workflow.

To keep releases/latest/download URLs stable, either publisher carries all five archives of the other released tool from previous latest only after validating its SHA256SUMS. An incomplete/corrupt carried set blocks publishing. No other product is rebuilt or relabelled; its embedded provenance remains its own. Every new latest has both released products' archives, one combined SHA256SUMS and the publishing product's verification JSON. Available other-product verification metadata is also checksum-verified and carried forward, preserving existing latest metadata links; immutable tagged releases retain their originals.

Every archive includes the executable, README, Apache license/notice, Transfer reference/retention documentation, BUILD_INFO.json and licensing material from the exact building Go toolchain. The result recorder runs formatting, release guards, vet, repository-wide race tests, both command builds, executable delivery/restart/interruption and TLS checks. Large-file assembly verification measures total Go allocations for a sparse 64 MiB plus 17-byte source and enforces a bound independent of the complete file; recorded values describe that environment, not all maximum-size transfers. Public asset/checksum/download verification is required after automated publication before adding website download links.

Transfer 0.1.0 was automatically published from 8ad7097055a06ab3720714b4b00d0e37ca993d3c after stable CI 39392321791 and Release Transfer 39392621965 passed. Public proof is in test/results/transfer-0.1.0-release. scripts/verify-public-transfer.py checks exported public tag/source metadata, all tagged/latest asset bytes, clean archive provenance and downloaded native smoke; use a fresh scratch download directory when repeating it. Inspect archives and its verification JSON were byte-for-byte preserved. The live website now links these verified assets.

## Transfer 0.2.0

Adds `bitspeed-transfer clean --root=DIR [--dry-run]`, which removes stored chunk files from completed sessions while the receiver is stopped. It holds the root lock, runs full startup recovery first, skips the serve-only write probe and leaves destinations, receipts, witnesses, journals, corrupt-chunk evidence and unfinished sessions untouched. See finalization.md for the exact rules. The delivery protocol, storage layout and platform scope are unchanged from 0.1.0, and 0.1.0 senders and receivers interoperate with 0.2.0. An independent review before release found no blockers; its should-fix items (dry-run wording, full-disk operation, platform check order) were fixed, and tests were added for damaged destinations, a write-less disk, directory sync failure and cancellation. The executable smoke now runs clean against a delivered root and restarts the receiver, and the Windows smoke checks that clean is refused without creating anything.

## Transfer 0.3.0

Adds progress output to `send` and `send --upload-only`. Lines go to stderr; the JSON result on stdout is unchanged. The first line reports how many chunks the receiver can already prove and how much will be sent, chunk lines follow at most once per percent of the bytes to send (bounded at about a hundred lines at the 16,384-chunk protocol limit), and a final line appears before finalization. A chunk counts only after the receiver's acknowledgement passes the full identity and digest check, and the finalize line uses the receiver's own verified count. Library callers get the same events through SendWithProgress and UploadOnlyWithProgress; Send and UploadOnly are unchanged. A progress write error stops the command, and a closed stderr pipe may end the process through SIGPIPE, as it already could during preparation; stored chunks remain verified and a rerun continues. Protocol, storage and platform scope are unchanged, so 0.1.0 to 0.3.0 senders and receivers interoperate. Independent review found no blockers; its findings on documentation, the finalize count and test coverage (stop at finalize, empty file, protocol-limit output bound) were addressed.

## Transfer 0.4.0

Adds Windows delivery. Every command (prepare, send, upload-only, status, serve and clean) works on Windows 10 version 1903 or later, Windows 11 and Windows Server 2022 or later, on local NTFS volumes on fixed drives. The protocol and storage layout are unchanged, so senders and receivers from 0.1.0 onward interoperate across Linux, macOS and Windows. windows-persistence.md maps each persistence step to its Windows call. Privacy is checked through access lists, sealed spool files carry no read-only attribute, flushes of read handles and directories go through a second write handle that must name the same file, and the receiver refuses network, removable, FAT, exFAT and ReFS volumes by examining the opened root. Token files may now end with a Windows line ending on every platform.

The whole Transfer test suite, including the process-kill recovery tests and race-enabled tests, runs on windows-latest in the separate Transfer Windows workflow together with the executable delivery, interruption and TLS checks; Release Transfer requires it for the exact commit, and the packaged Windows archive runs the same executable checks before publication. An independent review found no blockers. Its should-fix items were addressed: the filesystem gate now follows links to the real volume, the supported Windows versions were narrowed to those tested semantics cover, Windows results are kept as a workflow artifact, the public verifier handles releases before and after Windows delivery, and the Windows checks moved out of CI so they cannot block Inspect. Tests were added for the flush fallback, a path that no longer names the open file and a link to a network share. Linux and macOS behaviour is unchanged.
