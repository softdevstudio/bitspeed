# Transfer protocol and persistence contract

This is the proposed v1 contract for one file, one receiver and one sequential chunk upload. The manifest contract, command skeleton and local sender snapshot preparation/revalidation are implemented. Authenticated session creation, chunk staging and status are implemented as development operations. Upload restart recovery is implemented and tested with killed sender/receiver processes. Final assembly, full-file verification, no-replace destination publication and receipt recovery are implemented as development operations. The receiver accepts uploading, finalizing, completed and failed journals and blocks ambiguous binding metadata rather than guessing. Transfer stays at 0.0.0-dev and has no downloadable release. Inspect is independent.

## Commands and trust boundary

The planned commands are serve, send and status. Version/help and local send --prepare-only currently work. Development serve, status and explicit send --upload-only support chunk staging. Normal send completes delivery from a prepared snapshot and durably caches the verified receipt; no automatic source preparation or retry loop is implicit. See sender-spool.md for preparation/reuse flags and supported local filesystems.

The development serve command takes a private receiver root, a listen address and a token file. Direct TLS uses a certificate and key. Plain HTTP is allowed only on literal loopback addresses, including client URLs; a DNS name resolving to loopback does not qualify. Off-machine traffic requires HTTPS with normal certificate and hostname verification. There is no insecure TLS mode. Clients ignore proxy environment variables and never follow redirects. A TLS reverse proxy can connect to a loopback-only listener, but its authentication, TLS and access-log configuration remain the operator's responsibility; forwarded headers never expand the listener's trust boundary.

The token file holds exactly 64 lowercase hexadecimal characters from 32 cryptographically random bytes, optionally followed by one LF. Tokens are not command-line arguments, URL components, stored manifest fields or log content. Each endpoint requires Authorization: Bearer followed by that token. Compare fixed-length token bytes in constant time. Reject missing or invalid authentication with the same 401 response before revealing session existence or reading an application body. Authenticate status as well as writes. Do not log request headers, query strings, source paths or token-file contents. Configuration and client errors use stable codes rather than reflecting hostile input. One token grants access to the whole root; multi-user isolation and per-transfer permissions are outside v1.

The receiver root and its parent must be trusted and exclusively writable by the receiver account. The receiver must hold an OS-backed exclusive root lock for its entire lifetime; a PID file alone is insufficient. Reject symlinks, reparse points and unexpected filesystem types in managed paths. Do not traverse sender-provided paths. Another process with write access to the root is outside the integrity guarantee. Filesystem capability checks and actual failure tests are required before enabling a receiver platform.

## Manifest and identity

The manifest is a UTF-8 JSON object. Every field below is required exactly once, with exact spelling; unknown fields, duplicate keys, case aliases, nulls, fractional/exponent integers, trailing documents and nesting beyond the flat object plus hash array are rejected by the wire decoder. A typed Go struct alone is not a wire decoder. The decoder must enforce limits before allocating from untrusted lengths.

| Field | Contract |
| --- | --- |
| protocol_version | Integer 1 |
| transfer_id | 64 lowercase hex characters, generated from 32 random bytes once by the sender and persisted |
| file_size | Integer bytes, 0 through 68,719,476,736 (64 GiB) |
| chunk_size | Integer bytes, 65,536 through 16,777,216; default 4,194,304 |
| chunk_sha256 | Ordered array of lowercase 64-character SHA-256 strings; empty array for an empty file |
| file_sha256 | Lowercase 64-character SHA-256 of the entire immutable snapshot |

Chunk count is ceil(file_size / chunk_size), computed without overflowing an addition. It must equal the array length and must not exceed 16,384. Thus small chunks can impose a smaller effective file limit. All chunks except the last have chunk_size bytes. The last has file_size minus index times chunk_size bytes, where indices start at zero. An empty file has no chunks and the SHA-256 digest of zero bytes. Content-Type is application/json, with no content encoding. The maximum encoded manifest is 2 MiB. Wire JSON can contain insignificant whitespace and different key order; canonicalization removes those differences.

Canonical manifest bytes use the field order in the table, compact JSON with no whitespace or trailing newline, decimal integers, fixed ASCII field/string values and all fields present. Example:

```json
{"protocol_version":1,"transfer_id":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","file_size":0,"chunk_size":4194304,"chunk_sha256":[],"file_sha256":"e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"}
```

The manifest identity is lowercase SHA-256 of those canonical bytes. A transfer ID is permanently bound to its manifest identity. Reusing that ID with different canonical fields returns manifest_conflict and never changes the existing session. Two independently generated IDs may describe identical content; they are separate transfers. Hashes validate bytes against a manifest; they do not authenticate the source or provide application-consistent snapshots.

transfer/manifest.go implements typed shape validation, canonical bytes, identity and expected chunk lengths. Sender preparation verifies snapshot content and strictly accepts only canonical saved manifests on reuse. DecodeManifest enforces the bounded strict HTTP manifest shape.

## HTTP operations

Use /v1/transfers and exact paths below, without query parameters or redirects. Reject unexpected methods with 405 after authentication. All JSON responses have protocol_version 1; clients validate required fields and bounds before acting. Successful JSON responses and errors use application/json. Chunk requests use application/octet-stream with an exact Content-Length and no content encoding; unknown/chunked lengths are rejected. Reject unexpected bodies on GET. The transfer ID is one validated path segment; chunk indices use canonical unsigned decimal without leading zeroes except 0. All responses include Cache-Control: no-store.

| Request | Successful response and repeat behavior |
| --- | --- |
| POST /v1/transfers, manifest body | 201 with status after durably admitting a new manifest; identical retry returns 200 with current verified status. Different identity at that ID returns 409 manifest_conflict. |
| GET /v1/transfers/{id} | 200 with verified status. Unknown ID returns 404 unknown_transfer. |
| PUT /v1/transfers/{id}/chunks/{index}, raw bytes | 200 with protocol_version, transfer_id, manifest_sha256, chunk_index, chunk_sha256 and stored true, only after verified durable publication. An identical stored chunk is revalidated and the same acknowledgement is returned. Request length and digest must still match; a duplicate cannot bypass validation. |
| POST /v1/transfers/{id}/finalize, body {"manifest_sha256":"..."} | 200 completed status only after final verification and publication. A repeated request returns the same receipt after verifying its published file. Missing chunks return 409 chunks_missing; a different identity returns 409 manifest_conflict. |

Status fields are protocol_version, transfer_id, manifest_sha256, state, verified_chunks, verified_bytes, missing_chunks, receipt and error_code. Counts are integers; missing_chunks is an ascending array of indices with at most 16,384 entries. verified_bytes sums exact lengths of verified chunks, never a saved counter. receipt is null until completed. error_code is null except in failed state. Maximum response size is 2 MiB. A completed receipt contains transfer_id, manifest_sha256, file_size, file_sha256 and output_name (the fixed basename {id}.data). Its content is stable across retries. No absolute receiver path is returned. Completed status still verifies the destination file; cleanup may leave verified_chunks zero and all chunks missing even though a valid completed receipt exists. State and receipt, rather than chunk count, establish completion.

All non-success responses have exactly protocol_version, error_code and retryable. Never return raw OS errors or echoed inputs. Errors before valid HTTP framing can be connection errors instead of JSON. Unknown sessions, malformed paths and invalid bodies must not cause filesystem writes. Fixed error bodies are small; clients cap error reads at 4 KiB. The upload client rejects duplicate/null/unknown response fields and checks status accounting and chunk acknowledgements against its local manifest.

| HTTP | Codes and effect |
| --- | --- |
| 400 | invalid_request, invalid_manifest, invalid_index; no admission or acknowledgement |
| 401 | unauthorized; same body for absent/incorrect token |
| 404 | unknown_transfer |
| 405 | method_not_allowed |
| 409 | manifest_conflict, chunks_missing, session_busy, destination_conflict, invalid_state, transfer_failed |
| 411 | length_required |
| 413 | limit_exceeded, including oversized manifest or chunk |
| 415 | unsupported_media_type or unsupported_encoding |
| 422 | chunk_length_mismatch, chunk_digest_mismatch, final_digest_mismatch |
| 503 | storage_unavailable, capacity_exhausted, recovery_required |

retryable is true only for session_busy, chunks_missing, storage_unavailable, capacity_exhausted and recovery_required. Retry with bounded backoff after status; never silently create a new ID to mask a failure. Destination conflicts and verified final digest failures make a session terminal failed once its failure record can be persisted. A conflicting manifest request leaves the existing session unchanged. Bad chunk requests leave the previously verified state unchanged. Chunk PUT is allowed only in uploading; finalizing/completed return 409 invalid_state. Finalize is allowed in uploading (all chunks present), finalizing (recovery/retry) and completed (same verified receipt). Storage failures never acknowledge new progress; if failure state cannot itself be persisted, return 503 and recover from files on the next attempt. Status on a persistently failed session returns 200 with state failed and its stable error_code; mutation returns 409 transfer_failed. Authentication/transport failures cannot count as success.

## Bounds and admission

Fixed protocol limits are the manifest/chunk/file/count bounds above. Local receiver policy may reduce them. Initial defaults admit at most 16 retained sessions and reserve at most 256 GiB; configuration can reduce either. Reserve 3 times file_size plus 32 MiB per admitted session before writing its manifest. This covers valid chunks, at most one bounded corrupt evidence file per index, and the assembly. ready and the published output are hard links to that assembly, not extra full copies. On startup, reconstruct every retained session under this rule, including sessions from earlier two-copy builds. If the new total exceeds configured policy, refuse startup without rewriting bindings or deleting evidence. The allowance is not a promise about physical filesystem overhead. Retained completed/failed sessions keep their reservation until explicit offline removal. Quota checks and admission are serialized under the root lock. Reject admission that would exceed policy or available capacity with required safety headroom. Free-space checks are advisory: ENOSPC, quota exhaustion or later I/O failures still need safe handling. Do not evict another session to admit a new one.

Allow one in-flight mutating request globally; return session_busy for additional mutations rather than buffering file bodies. Status and mutations are serialized per session so verification cannot race publication or cleanup. Upload timeouts bound each request: default header timeout 10 seconds, body/operation timeout 5 minutes and client overall attempt timeout 6 minutes; slow links may require configured bounded larger durations. Header bytes are capped at 16 KiB and JSON bodies at 2 MiB. Streaming buffers stay bounded independently of file size. Cancellation is checked between reads and persistence stages; it never skips a required synchronization before an acknowledgement.

## Sender preparation and states

The sender transitions preparing to uploading only after a complete immutable snapshot and manifest have been durably published in its private spool. It copies from a stable regular source into a temporary snapshot with bounded buffers, records source identity/size/modification metadata before and after, and rejects observable changes. An unchanged metadata check does not prove an application-consistent snapshot of a changing source. Require a quiescent source. Calculate chunk and whole-file hashes from the completed snapshot, not from a second read of the original path. Synchronize snapshot data, publish it and synchronize the spool directory; publish the canonical manifest with the same temporary-write/sync/rename/directory-sync sequence. A directory with a manifest is usable only after snapshot size and hashes revalidate. No network admission occurs earlier.

A crash in preparing leaves no usable manifest; discard incomplete temporary files and restart preparation explicitly. Once uploading, resumes use the same snapshot/ID and the receiver's verified missing list. Revalidate the snapshot before reuse; source changes after preparation do not affect it. Chunk-send acknowledgement loss is resolved by querying status and retrying the same chunk, not increasing a local counter. A timeout or cancelled send preserves the spool. finalizing means all chunks are verified and a finalize request may have been sent. After a lost final response, status can establish completed using the immutable receipt. Only then does the send command exit zero. Locally cache a durable receipt before allowing manual spool removal. The initial version has no automatic spool deletion or background retry agent.

## Receiver storage and recovery

The root contains sessions/{id}/manifest.json, chunks/{index}, temporary files, ready and completion.json, plus files/{id}.data. The fixed journal name is journal.json. Its required fields are protocol_version (1), manifest_sha256, state (uploading, finalizing, completed or failed) and error_code (null except for a terminal failure). Validate its identity against the immutable manifest and reject unknown, duplicate or null required fields, except nullable error_code. Metadata decoding is bounded by 2 MiB. Session directories are created exclusively, never by concatenating an unchecked path segment. Both directories must be on one supported local filesystem. Files and root permissions restrict other users. Durable metadata writes mean write temporary, sync file, rename to the intended name, then sync its parent directory. Directory creation also requires syncing its parent. Admission persists the manifest and an uploading journal before returning status. A successful operation cannot ignore any sync or close error.

| State | Evidence and restart action |
| --- | --- |
| preparing | Sender only; no receiver session until manifest admission. Incomplete receiver admission directories are not advertised as progress. |
| uploading | A durable valid manifest exists. On startup, revalidate manifest and each published chunk by exact length and digest before serving that session. Remove incomplete temporary chunks; quarantine invalid published chunks and mark them missing. Never trust a progress counter. |
| finalizing | Durable intent binds the same manifest and fixed output name. Resume verification/assembly or reconcile ready and the published output; do not create another destination. |
| completed | A durable receipt and matching complete published file exist. Reverify size and full digest before reporting completed, including after restart. A missing/damaged output becomes failed storage_corrupt, never completed. |
| failed | A durable integrity/conflict failure record exists; no automatic reset, new manifest or final publication. Operator intervention requires stopping the receiver and preserving evidence. |

Malformed or missing manifests/journals, or a malformed receipt when present, block that session with 503 recovery_required and no mutations until offline operator intervention. A receipt is normally absent in uploading and before completion in finalizing. A missing receipt blocks only a session whose journal says completed. Do not invent a manifest identity or a completed/failed status when its binding metadata cannot be trusted. With valid binding metadata, damage to a completed destination can be durably recorded as failed with error_code storage_corrupt. Unrecognized orphan directories are preserved and block startup/admission because their binding and reservation cannot be established safely. Do not silently delete possible published data or guess their ownership. Recovery is bounded by the file/session limits and runs before serving progress for an affected session. Before advertising recovered progress, re-sync every revalidated chunk file and its containing directory, plus session/admission metadata and their containing directories, in persistence order. Finding valid bytes after restart is not proof that the interrupted persistence sequence completed. A sync/close failure returns storage_unavailable (or recovery_required if identity is uncertain), with no success status or chunk acknowledgement. Identical retry acknowledgements require this same gate, even when a valid chunk name already exists.

Revalidating all chunk bytes on every status is intentionally conservative for v1; a later cache needs a separate integrity contract. Missing or corrupt chunks in uploading are repairable by re-upload; damage to completed output is terminal. A process crash that loses a request response does not change the required verification rules.

For a new chunk, stream to a receiver-chosen exclusive temporary file in that session. Enforce exact length and hash while reading; reject excess bytes. Sync and close the verified file, atomically publish its fixed chunk name without replacing a different file, and sync the chunks directory before acknowledging. Serialize duplicates, validate the incoming duplicate body and the existing chunk, then acknowledge only matching bytes. A valid chunk published before a crash remains recoverable even when no acknowledgement reached the sender. Invalid bytes never become verified progress. Interrupted temp writes are never resumable partial chunks in v1.

## Final publication and platform gate

Finalization first persists intent for the manifest and fixed output name. Stream verified chunks in order into an exclusive temporary assembly in the session directory; verify exact total size and whole-file SHA-256. Empty files follow the same path with no chunk reads. On mismatch, persist final_digest_mismatch, keep evidence and publish nothing. Sync/close a valid assembly, rename to ready, then sync the session directory. Keep ready as a recovery witness. The finalizing intent is the journal in finalizing state, binding the immutable manifest and therefore the fixed output name.

On supported Unix local filesystems, create a hard link from ready to files/{id}.data. This must be a no-replace operation: never rename over or truncate an existing destination. If the destination already exists, accept it only when filesystem identity proves it is the same file as retained ready and its size/digest match; identical bytes in an unrelated file are still a destination conflict. Sync the files directory after linking. Persist completion.json with the immutable receipt and sync its directory, then persist a completed journal before acknowledging completion. Retain ready and intent until that receipt is durable. On retry/restart, reconcile the witness and destination, repeat full verification and required directory syncs, and persist the same receipt. A valid receipt plus matching published file can recover a finalizing journal to completed after re-verification and completion of all required file/directory synchronizations. A completed journal without a trustworthy receipt is recovery_required. If receipt exists but destination is invalid, report failure. A lost success response cannot produce a second destination name. If finalizing has neither ready nor a destination, revalidate chunks and restart assembly. Missing/damaged chunks can return that session to uploading only after a durable state update and proof that no destination was published. Discard the incomplete assembly temp and sync the session directory, then atomically replace the finalizing journal with an uploading journal (same manifest identity, null error_code), sync its directory and only then report uploading or accept PUT. The uploading journal replaces the old intent; do not reuse a stale finalizing state. If a valid ready exists, finish publication from it even when chunks are missing. An invalid ready is recovery_required rather than an automatic repair transition. If a destination exists without a trustworthy witness/receipt, block with recovery_required; never infer ownership from equal bytes.

The first receiver implementation targets Linux and macOS local filesystems with working file sync, directory sync and same-filesystem no-replace hard links. Refuse receiver startup if its required operations are unavailable, the root is shared by another receiver or its filesystem is unsupported. Capability probes do not prove hardware crash behavior. Network filesystems, object mounts and filesystems without the required persistence contract are unsupported. Windows receiver enablement is blocked until a documented native publication/synchronization implementation and crash tests establish equivalent guarantees; a future Windows binary can still support sender/status while rejecting serve clearly. Building a Windows binary is not receiver durability validation. Session eleven decides and labels the actual release coverage.

Durable means the documented synchronization calls succeeded on a supported filesystem; storage hardware, mount settings and external modification can defeat stronger power-loss guarantees. Inject write, sync, close and link failures, plus process kills between each stage. Do not claim all hardware power-loss behavior from process-kill tests alone.

## Retention and acceptance tests

V1 performs no online or automatic cleanup. Retain sender snapshots, receiver chunks, ready, manifests and receipts until the operator deliberately removes a session offline after confirming completion. Removing a receiver receipt ends retry idempotency for that ID; the retained destination then blocks re-publication as a conflict. IDs must never be deliberately reused. Disk cost and the offline cleanup procedure are documented in finalization.md. Later online cleanup requires a new tested recovery transition.

Subsequent sessions must test snapshot cancellation/changes/space failures; authenticated bounded admission; malformed/duplicate JSON; wrong chunk lengths/hashes; concurrent requests; temporary and published chunk crashes, including a kill after chunk publication but before directory sync followed by an injected recovery-sync failure; lost acknowledgements; restart revalidation; interrupted assembly; link/dir-sync/receipt failures; conflicting destinations; empty and partial last chunks; corrupt manifests/journals/receipts; and full-digest disagreement despite individually correct chunks. SIGKILL and injected disk failures both matter. A successful end-to-end test ends with one verified published file and a repeatable receipt after restarting both processes. Receiver chunk staging, upload recovery, assembly, final publication and receipt recovery are implemented as unreleased development operations. The release-candidate hardening and platform gate remains session eleven. See receiver-staging.md for current development limits. Local sender preparation and reuse checks are described in sender-spool.md.
