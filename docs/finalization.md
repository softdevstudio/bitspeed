# Verified delivery and retention

Transfer is an unreleased 0.0.0-dev build. Linux/macOS development delivery is implemented; release-candidate hardening and platform validation are still required. Inspect remains independently released. Build Transfer from source and follow receiver-staging.md for a private token, supported filesystem, receiver root and prepared sender snapshot. Keep the source stable during preparation. Normal delivery uses the existing snapshot, never the original source:

```sh
bitspeed-transfer send --spool=/private/parent/sender --reuse=TRANSFER_ID --url=http://127.0.0.1:8080 --token-file=token
bitspeed-transfer status --url=http://127.0.0.1:8080 --id=TRANSFER_ID --token-file=token
```

Use verified HTTPS off machine. Send uploads missing chunks and requests finalization with the canonical manifest identity. Only completed status with a matching receipt can produce transferred true. The sender saves receipt.json with checked write, sync, close, atomic rename and directory sync before success. A local cache failure exits nonzero even if the receiver completed; repeat the same command. A cached receipt alone is never treated as current receiver verification. Upload-only remains available as an explicit staging operation and never claims transferred true.

## Persistence sequence

A finalizing journal durably binds intent to the immutable manifest and fixed output name. Assembly streams verified chunks into exclusive assembly.tmp with a 32 KiB buffer. It checks per-chunk hashes and the complete digest, syncs/closes the file, re-reads its saved bytes, renames it to ready and syncs the session directory. Empty files follow the same sequence. A whole-file digest disagreement becomes durable failed final_digest_mismatch and publishes nothing. A bad or incomplete assembly is never completion evidence.

Publication hard-links ready to files/TRANSFER_ID.data without replacement. A pre-existing destination is accepted only if it is the same inode as ready; equal bytes in an unrelated file remain a conflict. The receiver synchronizes the output directory, writes/syncs/renames completion.json, then writes/syncs/renames the completed journal. Before returning completed, it verifies the destination against the full manifest, synchronizes the receipt and metadata, and returns a stable receipt containing transfer_id, manifest_sha256, file_size, file_sha256 and output_name. No private absolute path is returned.

All mutations remain serialized under the receiver root lock. PUT is unavailable in finalizing/completed and all failed sessions reject mutation. Finalize accepts only a bounded exact manifest_sha256 object and refuses a different identity. Missing chunks return chunks_missing. Status can durably return an interrupted finalizing session to uploading only after establishing that neither a ready witness nor a destination exists, discarding recognized bounded assembly.tmp and synchronizing the uploading journal. Malformed receipts or bindings block recovery rather than being guessed.

## Restart and failures

A finalizing session with valid ready resumes publication even when retained chunks are missing. An output already linked to that witness is reverified and synchronized, never published under a second name. An existing valid receipt is preserved across retries. Completed recovery verifies full destination bytes and witness identity before serving completed. Missing/damaged output after a trustworthy completion receipt becomes failed storage_corrupt; malformed completion metadata remains recovery_required. Storage read/write/close/sync failures cannot report completion. A lost final HTTP response is resolved by restarting the same processes with the same root/spool/ID and repeating send. Completed status can have missing retained chunks; the receipt and verified destination establish delivery, and the sender does not attempt to upload those chunks again.

Every startup reconstructs reservations at three times file size plus 32 MiB, including older two-copy sessions. Policy excess blocks startup without modifying bindings. The reservation covers chunks, one bounded corrupt evidence file per index and the assembly; output and ready are hard links. Physical admission checks conservatively include prior reservations, and finalization checks free space again. Checks are advisory: later ENOSPC, quota or device failures still fail safely. File and directory count scans are bounded. Startup and HTTP operations have five-minute limits; very large/slow storage can require operator attention rather than bypassing verification.

Process tests kill at finalizing journal rename, assembly write, ready rename, output link, receipt write/rename and completed journal rename. Recovery includes injected output-directory sync failure after witness revalidation. Fault tests cover intent, assembly, ready, destination, receipt and completed metadata writes, short/corrupt writes, close, sync, rename and link errors. Tests also cover missing/corrupt chunks, foreign destinations, full-digest disagreement, empty files, partial last chunks, malformed receipts, missing witnesses, sender cache failures and lost final responses. These are process-crash and injected-I/O results, not hardware power-loss guarantees.

## Offline retention procedure

V1 performs no automatic cleanup. Retain sender snapshots, valid chunks, corrupt evidence, ready, receipts and journals. Keeping ready preserves the identity witness; deleting completion metadata or reusing an ID breaks recovery. An interrupted assembly or metadata temporary file is removed only through its recognized bounded recovery transition. Failed evidence remains for investigation.

Before intentional cleanup, query completed status and independently verify the destination digest against the immutable receipt. Save the receipt outside the managed roots. Stop the sender and receiver and ensure no process owns either root; preserve a backup when investigating failure. A sender session directory may then be removed offline once its snapshot is no longer needed. Removing a receiver session requires removing its matching managed destination together, so first copy the delivered file outside the managed root and verify that copy's size/digest. Remove only the exact session directory and its matching destination under that stopped dedicated root. Leave other sessions intact, restart the receiver, and verify their status. Never remove just ready, a journal or a receipt from a retained session. Never reuse the old transfer ID. A retained destination without its session binding deliberately blocks startup and must not be adopted based on equal bytes. There is no online deletion API or automatic eviction.
