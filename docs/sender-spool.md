# Local sender snapshots

Transfer's development command can prepare or revalidate a local snapshot on Linux and macOS. It sends no HTTP requests. Version remains 0.0.0-dev; there is no Transfer release. Windows preparation fails with an unsupported-platform error before file activity. Cross-compilation does not establish persistence support.

Use send --prepare-only --source=FILE --spool=DIR, optionally --chunk-size=BYTES (default 4194304). Options require =VALUE; unknown or duplicate options are rejected without reflecting values. For reuse, use send --prepare-only --spool=DIR --reuse=ID, without a source or chunk-size option. JSON stdout contains prepared true, transferred false and the canonical manifest as a nested object. Human progress on stderr reports stage and byte counts; neither output persists the source path. Success means a locally prepared snapshot, not delivery to a receiver. Interrupted stdout can leave a safely prepared directory without a printed ID; inspect the private spool directories and reuse the saved ID rather than editing metadata.

Provide a dedicated spool beneath a trusted existing parent. The command creates the final spool directory with mode 0700 if missing; it does not create intermediate parents. Existing spools must have mode 0700. The spool itself cannot be a symlink, including with trailing slash/dot spellings. Parent components must be trusted against replacement. Other processes with the same account's write privileges can defeat read-only permissions, so external mutation of the spool is outside the guarantee. Source files must be regular, quiescent files; a final source symlink is rejected. Unix source opens are nonblocking/no-follow so replacement with a FIFO or symlink cannot silently change the file type. Observable identity, size and modification-time changes are checked against both the open descriptor and path. Metadata checks cannot detect every possible modification or establish an application-consistent snapshot of an active file.

The spool holds a permanent .lock file and directories named by 64-character lowercase hexadecimal transfer IDs. An OS-backed nonblocking exclusive lock covers cleanup, preparation, publication and reuse. Never delete or replace .lock; another process can then lock a different inode. Lock contention fails clearly. Only one preparation/revalidation uses a spool at a time. IDs use 32 cryptographically random bytes. An existing ID is never deliberately replaced. The private parent, lock and cooperating-writer requirement make the checked directory rename exclusive; the design does not defend against a hostile same-account writer racing filesystem operations.

Preparation requires advisory available capacity of source size plus 32 MiB headroom before copying. Files and chunk counts retain the protocol bounds. At most 64 root entries, including .lock and pending work, are accepted; a full spool rejects new preparations. Space checks do not reserve physical disk space. Later ENOSPC, quota or storage errors still fail without a success claim. Retained snapshots consume their full file size plus metadata; there is no automatic cleanup of complete snapshots. Do not place the source inside its managed spool.

A new preparation lives in .preparing-ID with fixed names snapshot and manifest.json. Copy uses a 32 KiB buffer and hashes the observed copied bytes. Hash the completed saved snapshot in a second bounded pass, computing full-file and ordered chunk digests from the saved bytes. Require its whole-file digest to match the copy-pass digest, catching changed storage bytes before manifest publication. No whole-file or whole-chunk buffer is allocated; hash metadata is bounded by 16,384 chunks. Empty files use an empty hash array and the SHA-256 of zero bytes. A stable original source is required only during the copy; later original-file changes cannot alter the saved snapshot.

Synchronize the read-only snapshot (0400), then write the validated compact canonical manifest, mark it 0400, synchronize and close it, and synchronize the preparation directory. Only then rename the directory to ID under the held lock and synchronize the spool. Synchronize the spool parent on every open, including reuse, to complete a creation sequence interrupted before its parent sync. Any data/metadata write, short write, sync or checked close failure yields no successful preparation. The lock close only releases exclusion; it does not represent a data persistence boundary. Cancellation is checked between copy/hash reads and before/after publication; an already-published directory may remain after cancellation or a parent-sync error and must be revalidated before reuse.

After a process restart, locked preparation/reuse scans the bounded root and discards .preparing-ID directories only when their contents have recognized names and are regular files. It removes only those files and their directory, then synchronizes the spool. Symlinks, unexpected entries or directory modes block cleanup; it never recursively follows paths or deletes an unexplained tree. Pending work is never advertised as reusable, even if manifest.json was already written. Cleanup failure remains an error; incomplete evidence may require offline inspection. A new preparation uses a new ID after cleanup.

Reuse validates the ID before filesystem access, requires an exact two-file directory with read-only regular files, bounds the manifest read at 2 MiB, validates its typed schema and requires byte-for-byte equality with canonical encoding. Duplicate, alias, unknown, missing and malformed local fields therefore fail. Noncanonical whitespace/key order also fail intentionally for this private format; future HTTP wire decoding has a different acceptance contract. Reuse rehashes all saved bytes and compares the full canonical manifest, checks file metadata stability, and re-synchronizes snapshot, manifest, session directory, spool and parent before success. Recovery-sync failure or cancellation cannot report a reusable snapshot. The original source is not opened. Corrupt complete snapshots are retained and rejected, never silently repaired or rebound to another manifest.

Local process-kill tests stop preparation during copying, after manifest write and after directory publication before parent synchronization. Restart discards pending directories or verifies and synchronizes a published one. Failure injection exercises write/short-write/corrupt-write, each checked sync/close boundary, publication rename, capacity checks and recovery synchronization. Tests also cover empty and partial chunks, changed/replaced sources, cancellation, locks, damaged metadata/data and unsafe cleanup paths. A sparse 32 MiB source allocation check exercises bounded memory; recorded conditions and outcomes are under test/results. These tests establish tested software behavior on CI filesystems, not every hardware power-loss guarantee. Filesystems without working file/directory synchronization, remote/object mounts and untrusted/shared parents are unsupported. Receiver endpoints, chunk uploads, transfer resume and destination publication remain later work.
